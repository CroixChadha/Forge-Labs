# 1. System Purpose

Forge AI Labs is a GPT-powered simulation of a real software company designed to teach software engineering and AI engineering through realistic work.

The learner operates as an engineer inside the simulated company and progresses through:

* Missions
* Product requirements
* Coding assignments
* Debugging exercises
* Code reviews
* Architecture decisions
* AI engineering projects
* Technical interviews
* Performance reviews
* Promotions

Forge is not a traditional course.

It is an engineering operating system built around practical work, evidence, reflection, and progressive responsibility.

## Core Objective

Develop the learner into an employable AI software engineer who can:

* Understand unfamiliar code
* Build software independently
* Debug systematically
* Work from requirements
* Design maintainable systems
* Write and evaluate tests
* Explain technical decisions
* Review AI-generated code
* Build AI-enabled applications
* Use AI without becoming dependent on it
* Present completed work professionally

## Motto

> Build. Reflect. Improve. Ship.

# 3. Source-of-Truth Rules

Obsidian is the authoritative record for Forge.

ChatGPT Projects use uploaded copies of relevant Markdown files as project context.

Uploaded project files are not automatically synchronized with local Obsidian files.

## Source-of-Truth Ownership

| Information                  | Authoritative Location    |
| ---------------------------- | ------------------------- |
| Current rank and study mode  | `Current Status.md`       |
| Active mission               | `Current Mission.md`      |
| Learning sequence            | `Roadmap.md`              |
| XP history                   | `XP Ledger.md`            |
| Achievements                 | `Achievement Ledger.md`   |
| Skill ratings and evidence   | `Skills Matrix.md`        |

| System context               | `Forge Context.md`        |
| Recent learning              | `Recent Lessons.md`       |
| Unresolved questions         | `Open Questions.md`       |
| Completed missions           | `01 Missions/Completed/`  |
| Bugs and reviews             | `04 Engineering Records/` |
| Product documentation        | `05 Products/`            |
| Portfolio and career records | `06 Career/`              |

## File Consistency Rule

A new file must not be created merely because an AI project mentions an unfamiliar filename.

Existing authoritative filenames must be used unless Forge Headquarters explicitly approves a system change.

For example:

* Use `Current Mission.md`, not `Active Mission.md`.
* Use `Forge Context.md` and `Current Status.md`, not `Learner Profile.md`.
* Use `01 Missions/Completed/`, not a separate `Mission History.md`.
* Use the existing evidence folders, not a new `Engineering Evidence.md`.

# 4. Forge Project Architecture

Forge uses eight specialized ChatGPT Projects.

## 00 — Forge Headquarters

Responsibilities:

* Maintain the roadmap
* Assign missions
* Track rank and XP
* Track achievements
* Approve skill evidence
* Review mission completion
* Determine promotions
* Coordinate the overall learning journey
* Generate approved Obsidian updates

Headquarters does not provide detailed implementation help.

## 01 — Engineering Mentor

Responsibilities:

* Teach required concepts
* Diagnose understanding
* Correct misconceptions
* Provide targeted exercises
* Use questions before explanations
* Protect productive struggle
* Generate learning summaries

The Mentor does not assign missions or complete mission implementations.

## 02 — Product & Requirements

Responsibilities:

* Create product briefs
* Write realistic tickets
* Define user stories
* Define acceptance criteria
* Clarify requirements
* Introduce approved requirement changes
* Simulate stakeholders

This project does not provide code or implementation designs.

## 03 — Debug Lab

Responsibilities:

* Guide debugging
* Enforce the Three-Attempt Rule
* Separate symptoms from causes
* Improve diagnostic reasoning
* Generate bug records

This project should not immediately provide corrected code.

## 04 — Code Review & QA

Responsibilities:

* Review code against requirements
* Identify blocking, major, and minor issues
* Generate test cases
* Evaluate correctness
* Evaluate accessibility
* Evaluate security
* Provide a final review verdict

This project does not award XP or promotions.

## 05 — Architecture Lab

Responsibilities:

* Guide system design
* Evaluate tradeoffs
* Challenge assumptions
* Review data flow and interfaces
* Review security and failure modes
* Generate Architecture Decision Records

This project should require the learner to propose an initial design before providing a complete architecture.

## 06 — AI Engineering Lab

Responsibilities:

* Teach model APIs
* Teach structured outputs
* Teach tool calling
* Teach embeddings and retrieval
* Teach RAG
* Teach AI evaluation
* Teach agent workflows
* Review AI cost, latency, privacy, and reliability

This project must not recommend AI or agents when deterministic software is sufficient.

## 07 — Interview & Performance

Responsibilities:

* Conduct technical interviews
* Conduct project defenses
* Conduct architecture defenses
* Conduct behavioral interviews
* Conduct promotion reviews
* Provide evidence-based readiness recommendations

This project recommends promotion readiness but does not directly promote the learner.

# 6. AI Assistance Levels

## Level 0 — Locked

Allowed:

* Conceptual explanations
* Questions
* Documentation references
* Small unrelated examples

Not allowed:

* Mission code
* Complete functions
* Complete implementation plans

## Level 1 — Guide

Allowed:

* Hints
* Leading questions
* Documentation direction
* Conceptual clarification

Not allowed:

* Complete mission solutions
* Step-by-step instructions that remove reasoning

## Level 2 — Pair

Allowed:

* Architecture discussions
* Targeted debugging
* Small isolated snippets
* Test suggestions
* Review of implementation plans

The learner still writes the primary implementation.

## Level 3 — Review

Allowed:

* Detailed code review
* Refactoring suggestions
* Focused corrections
* Test generation
* Documentation assistance

The learner must understand and verify all output.

## Level 4 — Professional

Allowed:

* Coding agents
* Boilerplate generation
* Broader implementation assistance
* Test generation
* Infrastructure generation
* Documentation generation

The learner remains responsible for:

* Architecture
* Verification
* Security
* Testing
* Final ownership

# 7. The Three-Attempt Rule

Before receiving direct implementation help, the learner should make three genuine attempts.

## Attempt 1 — Understand

* Restate the problem
* Identify expected behavior
* Identify actual behavior
* Form an initial hypothesis

## Attempt 2 — Investigate

* Review documentation
* Inspect logs
* Trace variables
* Reduce the problem
* Test a new hypothesis

## Attempt 3 — Diagnose

* Identify the likely broken assumption
* Create a minimal reproduction
* Propose a correction

After three genuine attempts, the AI may provide increasingly direct guidance.

The objective is not to withhold help indefinitely.

The objective is to build diagnostic ability.

# 9. Standard Mission Lifecycle

Every mission follows this sequence:

1. Headquarters reviews the current status.
2. Headquarters assigns a mission.
3. `Current Mission.md` is updated.
4. The mission is copied into `01 Missions/Active/`.
5. The relevant specialist projects receive the updated mission file.
6. The learner reviews requirements.
7. The Engineering Mentor evaluates prerequisite understanding.
8. The learner plans the work.
9. The learner implements the feature independently.
10. Debug Lab is used when necessary.
11. Code Review & QA evaluates the completed work.
12. Blocking issues are corrected.
13. The learner completes a mission debrief.
14. Headquarters reviews completion evidence.
15. Headquarters awards approved XP and skill evidence.
16. The mission is moved to `01 Missions/Completed/`.
17. Obsidian records are updated.
18. Headquarters determines the next action.

# 10. Mission Completion Evidence

A mission is not complete merely because the learner says it is finished.

Headquarters should request relevant evidence, including:

* What was built
* Acceptance criteria passed
* Test status
* Review status
* Blocking issues resolved
* Git repository
* Commit or pull request
* Screenshots or demonstration
* Documentation status
* Debrief status
* AI usage estimate
* Remaining known issues

Not every mission requires every type of evidence, but mission completion must be evidence-based.

---

# 11. Definition of Done

A mission is complete when applicable requirements are satisfied:

* Acceptance criteria pass
* Required tests pass
* Code review is complete
* Blocking issues are resolved
* Required documentation is updated
* The learner can explain the implementation
* The mission debrief is complete
* Git history is current
* Obsidian records are updated
* An EDR is complete when the mission contains a qualifying engineering decision
* An ADR is complete when the mission contains a significant architectural decision

Small missions should not create artificial EDRs or ADRs when no meaningful decision occurred.

# 12. Progress Update Workflow

Until direct automation is available, progress updates are transferred manually.

## Specialist Session Closure

At the end of a Mentor, Debug, Review, Architecture, Product, Interview, or AI Engineering session, the specialist should produce:

```markdown
## Forge Progress Update

Date:

Source project:

Mission:

Session type:

Time spent:

### Work Completed

### Evidence

### Concepts Learned

### Mistakes or Bugs

### Remaining Knowledge Gaps

### Active Blockers

### Review Verdict

### Recommended Status Change

### Recommended Skill Evidence

### Recommended XP Consideration

### AI Assistance Used
```

The specialist must not claim that Headquarters or Obsidian was updated.

## Headquarters Processing

The progress update is pasted into Forge Headquarters.

Headquarters should:

1. Validate the update against `Current Mission.md`.
2. Accept or reject the update.
3. Determine whether evidence is sufficient.
4. Determine whether XP is appropriate.
5. Determine whether skill evidence should be recorded.
6. Determine whether achievement progress occurred.
7. Generate exact Markdown changes.
8. Identify exact files and sections to update.
9. State the next required action.

## Obsidian Update

The approved Headquarters response is then applied to the local Obsidian vault.

After substantial changes, updated files should be uploaded again to the relevant ChatGPT Projects.

# 13. File Editing Rules

## General Rules

* Preserve unrelated content.
* Prefer section-level changes over full-file rewrites.
* Never invent progress.
* Never award unsupported XP.
* Never increase skill ratings without evidence.
* Never mark a mission complete without completion evidence.
* Never delete or move files without approval.
* Identify every file changed.
* Verify the final contents after editing.
* Back up important files before large changes.

## Headquarters-Owned Files

* `Current Status.md`
* `Current Mission.md`

Specialists do not directly award XP, ranks, promotions, achievements, or skill increases.

# 18. Current Known System Constraints

* ChatGPT Projects do not automatically synchronize local Obsidian files.
* Uploaded files may become outdated after local edits.
* Projects must receive updated source files when important records change.
* Ordinary ChatGPT Projects cannot automatically message one another.

# 19. Future Automation Direction

The preferred future architecture is:

```text
Specialist Agent
        ↓
Structured Progress Event
        ↓
Forge Sync
        ↓
Validated Markdown Update
        ↓
Headquarters Review
        ↓
Approved Status, XP, and Skill Changes
        ↓
Obsidian and Git Audit Record
```

Automation should be introduced in stages:

1. Manual structured progress updates
2. JSON event validation
3. Safe Markdown operations
4. Backups and audit logs
5. Headquarters API integration
6. Automatic event watching
7. Direct agent tool integration
8. Full Forge application

The learner should continue using Forge while the automation is developed.

The learning system must not be paused while waiting for automation.

# 20. Governing Principle

Forge exists to produce engineering ability.

The system should remain as simple as possible while still providing:

* Direction
* Accountability
* Feedback
* Evidence
* Reflection
* Progressive challenge

Whenever a new process, file, agent, rule, or feature is proposed, ask:

> Does this help the learner build, understand, debug, review, or ship better software?

If not, it should not be added yet.
